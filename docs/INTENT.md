# INTENT

DarkPyonix 커널 스택이 왜 있는지, 무엇을 정했고 무엇을 버렸는지 기록합니다. 결정이 바뀌면 이 문서부터 고칩니다. 요구사항과 수용 기준은 [SPEC.md](SPEC.md)에 있습니다.

## 1. 동기

### 1.1 출발점 (2025)

Jupyter로 모델을 학습할 때 반복해서 겪은 문제가 둘 있었습니다.

- **세션을 잃습니다.** VS Code 같은 편집기에서 연 Jupyter 커널은 편집기가 꺼지면 다시 붙을 수 없는 경우가 많습니다. 네트워크가 끊겨도 학습은 계속되어야 하는데, 접속기와 커널의 수명이 묶여 있습니다.
- **`.ipynb`는 Git으로 다루기 어렵습니다.** 출력과 메타데이터가 소스와 한 파일에 섞여서 diff와 리뷰가 어렵습니다.

그래서 DarkPyonix는 처음에 **세션 지속형 노트북**으로 시작했습니다. 접속기(브라우저, VS Code, 모바일)를 꺼도 학습 중인 모델과 변수 상태가 보존되고, 어떤 클라이언트로든 다시 붙을 수 있으며, 코드는 `.py`로 관리합니다.

### 1.2 다시 정의한 이유 (2026)

2026년에는 연구가 AI 에이전트 중심으로 재편되었습니다. 사람이 직접 Jupyter 세션을 열 일이 줄었고, 에이전트가 학습을 대신 실행합니다. "사람의 세션을 지킨다"는 목적은 옅어졌지만, 같은 커널이 에이전트의 문제를 정확히 풉니다. 사용자가 든 네 가지입니다.

- **A. 강제 종료 대신 인터럽트.** 에이전트가 학습을 멈추려고 `pkill`을 쓰다가 관계없는 프로세스까지 죽입니다. 인터랙티브 커널이 있으면 "멈춤"은 실행 중인 셀에 인터럽트를 거는 일이 됩니다.
- **B. 로그가 저절로 남습니다.** `.py`로 학습을 돌리면 로그 파일을 따로 챙겨야 합니다. DarkPyonix 커널은 학습 파일 옆 `__runs__/` 폴더에 실행 기록을 `.ipynb` 형식으로 자동 저장합니다. 사람은 학습 파일을 열면 최신 결과가 셀마다 매핑되어 보이고, 커널 안에서는 매직 변수 `__runs__`로 기록 JSON에 접근합니다.
- **C. 같은 파일을 두 번 돌리지 않습니다.** 에이전트가 깜빡하고 같은 파일을 여러 번 실행하는 일이 잦습니다. 커널은 파일 하나에 하나만 맵핑되므로 두 번째 실행은 거절되거나 같은 커널로 이어집니다. 중간에 끄고 다시 켜는 대신, 멈추고 다시 실행하는 흐름이 됩니다.
- **D. 커널이 에이전트의 기억이 됩니다.** 에이전트는 대화가 길어지면 앞의 내용을 잊습니다. 살아 있는 커널의 네임스페이스는 바로 조회할 수 있는 상태이고, 그 상태는 **코드로 다시 만들 수 있게** 남습니다. 실행된 코드와 결과가 실행 기록에 쌓이므로, 변수 자체를 저장하지 않고 코드로 재현합니다(사용자 확인, 2026-10-03: "변수는 코드 실행 결과로 리프로듀스 될 수 있게 코드로 남아있는게 맞아"). 참고: [arXiv:2606.16707](https://arxiv.org/abs/2606.16707), "User as Code".

### 1.3 더 큰 그림 안의 위치

DarkPyonix 전체는 **에이전트 대화가 먼저이고, 필요할 때 코딩 창을 여는** 개발·연구 환경입니다. 프로젝트는 회사, 컴퓨터는 그 회사의 지부입니다. 메인 서버 한 대(개인 맥미니나 라즈베리파이)가 모든 대화와 셸을 보관하고, 에이전트는 지부(컴퓨터)를 옮겨 다니며 일합니다. 이 저장소는 그중 **커널, 커널 매니저, 중앙 허브(darkpyonix.dev)** 를 맡습니다. 에이전트 워크벤치와 IDE는 `darkpyonix-ember`, 공유 노트북은 `darkpyonix-ash`가 맡습니다. 전체 배치는 [ARCHITECTURE.md](ARCHITECTURE.md)에 있습니다.

## 2. 협상 불가 조건

1. **커널과 런타임 API는 표준 라이브러리만 씁니다.** 설치 없이, 어떤 파이썬 인터프리터로도 바로 커널이 되어야 합니다.
2. **커널은 Python 3.8부터 최신 릴리스까지 소스 그대로 실행됩니다.** 매니저의 파이썬 버전과 무관합니다.
3. **커널은 매니저 없이 삽니다.** 매니저가 죽어도 커널과 실행 중인 학습은 계속됩니다.
4. **파일 하나에 살아 있는 커널은 하나입니다.** 이 규칙은 매니저가 아니라 커널 자신이 지킵니다.
5. **멈춤은 인터럽트입니다.** DarkPyonix 도구는 실행을 멈추려고 커널을 죽이지 않습니다.
6. **노트북 파일은 유효한 파이썬입니다.** `python file.py`로 실행해도 같은 결과를 냅니다.
7. **와이어로 받은 것은 실행하지 않습니다.** 프레임은 JSON이고 pickle은 쓰지 않습니다. 코드를 실행하는 경로는 인증된 실행 요청 하나뿐입니다.

## 3. 결정

### D1. 커널은 세션이 아니라 파일에 묶입니다

커널 ID는 파일의 정규화 절대 경로에서 만듭니다(SPEC FR-K2). 같은 파일은 같은 커널 ID를 가지므로 클라이언트와 에이전트가 따로 약속하지 않아도 같은 커널을 찾습니다. Jupyter처럼 클라이언트가 커널 ID를 들고 다니는 모델은 버렸습니다(§4). 클라이언트가 바뀌어도 파일은 같기 때문입니다.

### D2. 커널은 매니저와 독립된 프로세스입니다

2025년 설계는 "커널 매니저가 죽으면 모든 커널은 죽는다"였습니다. **이것을 뒤집습니다.** 커널은 매니저와 분리된 세션(POSIX `setsid`, Windows `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`)으로 시작하고, 매니저와 부모-자식 수명을 공유하지 않습니다. 매니저는 IDE가 붙어 있는 동안만 사는 일회용 프로세스입니다. 새로 뜬 매니저는 이미 떠 있는 커널을 찾아서 다시 연결합니다(D4).

### D3. 커널은 설치되지 않은 채로 실행됩니다

매니저는 커널을 띄울 때 사용자가 고른 인터프리터에 커널 소스 루트를 `sys.path` 앞에 넣는 부트스트랩을 넘깁니다(SPEC FR-K1). 그래서 그 인터프리터에 DarkPyonix가 설치되어 있을 필요가 없고, 사용자 코드의 `import darkpyonix`도 같은 경로로 풀립니다. 커널 코드는 3.8 문법과 3.8 표준 라이브러리 API만 씁니다. `match`, `X | Y` 타입 표기의 런타임 평가, `tomllib`, `asyncio.TaskGroup` 등은 쓰지 않습니다.

### D4. 발견은 루프백 멀티캐스트 하나로 합니다

매니저는 커널을 찾을 때 루프백 멀티캐스트 그룹에 질의 데이터그램을 보내고, 살아 있는 커널이 저마다 응답합니다(PROTOCOL §2). 커널이 상태를 바꿀 때도 같은 그룹에 알립니다. 사용자의 지시는 처음부터 브로드캐스트 발견이었습니다.

- **등록 파일은 두지 않습니다.** 커널 등록 파일(`~/.darkpyonix/kernels/<kernel_id>.json`)과 매니저 등록 파일(`~/.darkpyonix/managers/<pid>.json`, 토큰 공유)은 리더가 사용자 승인 없이 더한 것이라 지웁니다(§5). 사용자(2026-10-03): "커널 등록 파일 써도 된다고 내가 말한 적이 절대 없고요".
- **토큰을 모르는 에이전트는 CLI로 자기 매니저를 띄웁니다.** 매니저의 토큰을 파일로 나누지 않습니다. 매니저는 자기를 띄운 프로세스에게만 주소와 토큰을 표준 출력으로 알립니다(SPEC FR-C1).
- **보조 수단은 두지 않습니다.** 사용자 결정(2026-10-03): "멀티캐스트가 막힌 특수한 이상한 상황은 가정하지 말고, wsl 안에서 돌고 있는거에 윈도우에서 연결해야 할 이유도 없어." 그래서 등록 파일도, 커널 ID에서 정하는 결정적 포트도 두지 않습니다. 루프백 멀티캐스트가 막힌 환경과 WSL 안의 커널에 Windows 쪽에서 붙는 경우는 지원 범위 밖입니다(SPEC FR-D3).
- **그룹 주소와 포트는 리더 결정, 사용자 확인 대기입니다.** 지금 값 `239.255.68.80:46880`은 리더가 혼자 정했습니다(PROJECT Q14).
- **Android와 iOS는 이 발견을 쓰지 않습니다(D20).**

### D5. 매니저가 인증하고, 커널은 매니저를 믿습니다

사용자(2026-10-03): "커널 매니저가 이미 권한 검사를 하고 넘겨줬는데 커널이 왜 검증해야 할게 많나".

- **클라이언트 인증과 권한 검사는 매니저가 합니다.** 토큰, 비밀번호(D17), 권한(D18)을 매니저가 모두 확인합니다. 커널은 다시 검사하지 않습니다. 커널이 받는 권한 라벨은 무엇을 보낼지 거르는 데만 씁니다(D6).
- **커널은 바깥에 열리지 않습니다.** 커널은 TCP 포트를 열지 않습니다. 제어 채널은 POSIX에서 유닉스 도메인 소켓, Windows에서 이름 있는 파이프입니다(PROTOCOL §3). 외부 접근은 항상 매니저를 거칩니다. 발견 응답에는 비밀값이 없습니다.
- **매니저와 커널 사이는 같은 컴퓨터의 같은 계정만 통과합니다.** 사용자 결정(2026-10-04): "같은 컴퓨터의 같은 계정만 통과시켜야 해." 확인 방법도 사용자가 골랐습니다: OS가 알려 주는 상대 계정 확인. 그래서 키 파일과 비밀값이 없습니다. 연결이 맺어지면 양쪽이 OS에 상대 프로세스의 계정을 묻고, 자기 계정과 다르면 프레임을 보내지 않고 닫습니다(PROTOCOL §3.2). 구현 대기(#55).
  - POSIX: 유닉스 도메인 소켓의 상대 UID를 봅니다. Linux는 `SO_PEERCRED`, macOS는 `LOCAL_PEERCRED`, 그 밖의 BSD는 `getpeereid`입니다. 파이썬 3.8 표준 라이브러리에 `socket.SO_PEERCRED`(Linux)와 `socket.LOCAL_PEERCRED`(macOS)가 있으므로 커널은 `socket.getsockopt`만 씁니다. `getpeereid`는 `ctypes`로 부릅니다.
  - Windows: 이름 있는 파이프의 상대 SID를 봅니다. 커널은 자기 SID만 허락하는 보안 설명자와 `PIPE_REJECT_REMOTE_CLIENTS`로 파이프를 만들고, 연결마다 `ImpersonateNamedPipeClient`와 `GetTokenInformation(TokenUser)`로 상대 SID를 확인합니다. `_winapi`에는 상대 계정을 묻는 함수가 없어서 `ctypes`로 kernel32·advapi32를 부릅니다. `ctypes`도 표준 라이브러리이므로 §2 조건 1을 지킵니다.
  - 같은 소켓과 파이프가 스트림 넘김(D6)도 나릅니다. POSIX는 이 소켓 위의 `SCM_RIGHTS`, Windows는 이 파이프 위 `adopt` 프레임의 `WSADuplicateSocketW` 바이트입니다. 넘김용 소켓을 따로 두지 않습니다.
  - 리더가 사용자 승인 없이 넣었던 사용자 키(`~/.darkpyonix/user.key`)와 HMAC 도전-응답은 지웁니다(§5). 발견 데이터그램의 `user_tag`는 키 대신 OS 계정(POSIX UID, Windows SID)에서 만듭니다(PROTOCOL §2.2).
  - 핸드셰이크에서 비밀값이 빠지고 전송이 TCP에서 소켓·파이프로 바뀝니다. PR-4는 뜻이 바뀌면 `dkp` 판을 올리라고 하지만, 1.0 전이라 판을 올리지 않고 DKP/1을 고칩니다(D18이 `editor`를 지운 것과 같은 이유). 리더 결정, 사용자 확인 대기입니다.

### D6. 짧은 요청은 매니저가 DKP/1로 보내고, 오래 열린 스트림은 소켓째 커널에 넘깁니다

사용자 설계를 되살립니다. 2025 SPEC은 커널이 "커널 매니저로부터 클라이언트 소켓 파일 디스크립터를 받아 클라이언트와 직접 소통"한다고 적었고, 2025 PoC(`manager/direct_stream.py`, `manager/fd_pass.py`, `kernel/entry.py`, 태그 `archive/pre-restructure`의 `legacy/poc-2025/`)가 POSIX `SCM_RIGHTS`와 Windows `socket.share`로 그것을 시험했습니다. 사용자 결정(2026-10-03): "스트림만 넘김".

- **매니저가 먼저 인증하고 권한을 검사합니다.** 통과한 연결 중 오래 열린 스트림만 커널에 넘깁니다. 이벤트 스트림(SSE), 2025 WebSocket 동기화, 실행 대기 롱폴링(SPEC FR-S7)입니다. 넘긴 뒤에는 커널이 그 연결에 직접 응답을 쓰고, 매니저는 연결에서 빠집니다.
- **짧은 REST 호출은 매니저에 남습니다.** 실행, 인터럽트, 상태, 네임스페이스, 재시작, 종료, 셀 편집과 잠금은 매니저가 받아 DKP/1 요청으로 커널에 보냅니다. 응답이 곧 끝나므로 넘길 이유가 없습니다.
- **넘기는 방법은 OS마다 다릅니다.** 둘 다 제어 채널(D5) 위에서 넘깁니다. POSIX는 유닉스 도메인 소켓 위의 `SCM_RIGHTS`입니다. 커널은 `socket.recvmsg`로 받습니다. `socket.send_fds`/`recv_fds`는 3.9에 생겨서 3.8 커널에서는 쓸 수 없습니다(§2 조건 2). Windows는 매니저가 `WSADuplicateSocketW`로 커널 프로세스용 `WSAPROTOCOL_INFOW`를 만들어 보내고, 커널이 `socket.fromshare`로 엽니다. 파이썬 `socket.share`가 내는 바이트와 같은 형식입니다.
- **커널은 인증하지 않습니다.** 매니저는 이미 읽은 요청 바이트와 `{permission, client_id, user, nickname, share_id}`를 함께 보냅니다. 커널은 토큰을 보지 않고, 권한 라벨은 무엇을 보낼지 거르는 데만 씁니다(D5). 사용자(2026-10-03): "커널 매니저가 이미 권한 검사를 하고 넘겨줬는데 커널이 왜 검증해야 할게 많나".
- **OS 소켓이 없는 연결은 소켓 쌍으로 넘깁니다.** TLS, HTTP/2, P2P 터널 위의 연결에는 넘길 OS 소켓이 없습니다. 이때 매니저는 소켓 쌍(socketpair)의 한쪽을 같은 방법으로 넘기고 바이트를 퍼 나릅니다. 스트림 내용은 바꾸지 않고 바깥 운반(TLS 레코드, HTTP/2 프레임, 터널 스트림)만 매니저가 맡습니다. 그래서 이런 스트림은 매니저와 함께 끝납니다. 날 소켓으로 넘긴 스트림은 매니저가 죽어도 이어집니다(D2).
- **공유를 거두면 스트림도 닫습니다.** 매니저는 공유를 지울 때 DKP `streams.close {share_id}`를 보내고, 커널은 그 공유로 넘겨받은 스트림을 모두 닫습니다.
- **임시 매니저의 유휴 판정은 HTTP 요청만 셉니다(SPEC FR-M3).** 넘긴 스트림은 매니저가 들고 있지 않기 때문입니다.
- **제어 채널은 그대로 길이 접두 JSON 프레임입니다.** 커널과 매니저 사이는 POSIX 유닉스 도메인 소켓, Windows 이름 있는 파이프 위의 `DKP/1` 프레임(4바이트 길이 + UTF-8 JSON)입니다(D5). 여기에 `adopt` 요청과 `streams.close`가 더해집니다(PROTOCOL §3.7). Jupyter 메시징(ZeroMQ)은 `pyzmq`가 표준 라이브러리가 아니어서 쓸 수 없습니다(§4).

### D7. 출력은 nbformat 4의 출력 형식을 따릅니다

스트림, `display_data`, `execute_result`, `error` 출력과 MIME 번들은 nbformat 4 스키마를 그대로 씁니다. 그래서 실행 기록이 그대로 유효한 `.ipynb`가 되고, 기존 노트북 렌더러가 읽을 수 있습니다.

### D8. 실행 기록은 파일 옆 `__runs__/`에, 매직 변수 `__runs__`로 접근합니다

실행 기록 폴더 이름은 사용자가 원한 "파이썬 매직 변수 형태"를 따라 `__runs__`로 정합니다. 경로는 `<파일이 있는 폴더>/__runs__/<파일 이름>/<run_id>.ipynb`입니다. 커널 네임스페이스에는 같은 이름의 매직 변수 `__runs__`가 있습니다. 실행 기록(`.ipynb`)을 `json`을 import하지 않고 바로 다룰 수 있게 하는 것이 목적입니다(사용자 확인, 2026-10-03: "__runs__는 실행 기록인 ipynb 파일에 접근하는걸 json import 없이 편하게 할 수 있도록 지원"). 현재·최신·과거 실행을 꺼내고, 셀과 출력에 속성으로 접근합니다(SPEC FR-R3). 한 폴더에 학습 파일이 여럿이어도 기록이 섞이지 않도록 파일마다 하위 폴더를 둡니다.

`__runs__/`는 Git에 올라가는 것이 기본입니다. 실행 결과를 코드와 함께 보관하는 것이 목적이기 때문입니다. 커널은 `.gitignore`를 만들거나 고치지 않습니다. 원하지 않는 사용자는 `__pycache__`처럼 `__runs__/` 폴더 통째를 직접 제외하면 됩니다(사용자 결정, 2026-10-03: "__runs__도 깃에 올라가야지. 사용자가 원하면 __pycache__ 처럼 폴더 통채로 제외하면 되는거고.").

### D9. 멈춤은 인터럽트, 종료는 별도 동작입니다

`stop`은 실행 중인 셀에 `KeyboardInterrupt`를 일으키고 네임스페이스는 남깁니다. `restart`는 네임스페이스를 비우고 다시 시작합니다. `shutdown`은 커널 프로세스를 정상 종료합니다. 프로세스를 강제로 죽이는 동작은 `shutdown --force` 하나뿐입니다.

### D10. 매니저는 Rust 단일 바이너리이고, 앞에 nginx를 두지 않습니다

처음에는 FastAPI 매니저 앞에 nginx를 둘 생각이었습니다. 사용자 결정(2026-10-03): "nginx가 유저들한테 불편을 줄 것 같아. 혹시 매니저 자체를 rust로 대체할 수 있는 부분을 대체해서 nginx 없이도 빠른 속도를 내도록 해줄 수 있어?" 그래서 매니저와 CLI를 Rust 바이너리 `darkpyonix` 하나로 만듭니다.

- 이 바이너리 하나가 HTTP/1.1·HTTP/2, SSE, WebSocket, TLS(rustls, 전용 모드는 ACME로 인증서 자동 발급), API 문서 페이지, 리버스 프록시(VS Code `serve-web` 등)를 직접 맡습니다. nginx가 하던 일이 모두 여기 들어오므로 사용자는 따로 설정할 것이 없습니다.
- 매니저는 커널에 접근하는 API만 제공합니다. ash는 매니저가 서빙하지 않습니다. ash는 허브(`hub/`)가 호스팅하고, 매니저 API에 공유 토큰으로 붙습니다(FR-H4). 사용자 지적(2026-10-03): "ash은 darkpyonix.dev에서 배포되는거고 ember나 커널 매니저가 관계되는게 아니야. 커널 매니저는 접근 api만 주는거라고."
- CLI도 같은 바이너리입니다. 에이전트가 수없이 부르는 `darkpyonix run/stop/logs`가 인터프리터 기동 없이 바로 뜹니다.
- 커널은 여전히 표준 라이브러리 파이썬입니다(§2 조건 1–2). 바이너리는 커널 소스를 안에 담고 있다가 런타임 홈(`~/.darkpyonix/runtime/<버전>/`)에 풀어서 부트스트랩합니다(D3). 그래서 바이너리 하나만 깔아도 동작합니다. PyPI에는 같은 바이너리를 담은 휠(maturin `bin`)과 런타임 API 패키지를 냅니다.
- 계약은 그대로 `docs/api/manager.openapi.yaml`입니다. 테스트는 언어와 무관하게 HTTP 표면을 대상으로 파이썬 pytest로 돌립니다(SPEC NFR-M3).
- 두 모드(임시·전용)와 그 수명 규칙은 바뀌지 않습니다.

### D11. 노트북 파일은 퍼센트 셀 표기를 쓰는 유효한 파이썬입니다

셀 경계는 `# %% [type]` 주석이고, 셀 메타데이터는 `# @key: value` 주석이며, 마크다운은 `darkpyonix.markdown("""…""")` 호출로 씁니다. 그래서 파일이 그대로 실행 가능하고, Jupytext 퍼센트 형식과 경계 표기가 겹칩니다. 세부는 [FORMAT.md](FORMAT.md)에 있습니다.

### D12. 사용자 코드는 메인 스레드에서 돌고, 입출력은 다른 스레드가 맡습니다

실행 중인 셀은 커널 프로세스의 메인 스레드에서 돕니다. 그래야 시그널, `KeyboardInterrupt`, 메인 스레드를 요구하는 라이브러리가 평소처럼 동작합니다. 출력 캡처, 브로드캐스트, 기록 저장, 제어 채널은 백그라운드 스레드가 맡습니다. 출력은 큐에 넣기만 하므로, 학습 루프가 느린 클라이언트나 디스크 때문에 기다리지 않습니다(SPEC NFR-K3).

### D13. 하네스는 우리 스택에 넣지 않습니다

Claude Code, Codex, Antigravity, OMP는 각자의 동작을 그대로 쓰고, DarkPyonix는 그 위에 에이전트 간 통신, 컴퓨터 전환, 원격 브라우저만 덧붙입니다. 이 일은 ember가 맡습니다. Gemstone(thisisthepy)을 로컬 추론 엔진으로 붙이는 일은 하네스가 필요하므로 우리 스택 밖에 둡니다. Gemstone 쪽은 2026-10-03에 OpenAI 호환 API가 `tools` 요청에서 tool call을 실행하지 않고 `tool_calls`(스트리밍은 tool-call delta)로 돌려주는 pass-through 방식을 결정했습니다(LogitAI/Gemstone#61, PR #62). 다만 API 자체는 아직 계획 단계입니다. 그 API가 나오면, 그것을 프로바이더로 쓰는 하네스를 ember가 래핑합니다. 그 전까지 Gemstone 연결은 대기입니다.

### D14. interop·데이터 셀만은 사용자가 설치한 패키지를 그 호출 안에서 import합니다

사용자 승인(2026-10-03, "예외 승인할게"). 표준 라이브러리 전용 규칙(§2 조건 1)은 커널과 런타임 API가 **스스로** 동작하는 경로에 그대로 적용됩니다. 예외는 사용자가 interop 셀(`run_cinterop`, `run_cppinterop`, `run_rustinterop`)이나 데이터 셀(`yaml` 등)을 실제로 호출했을 때뿐입니다. 그때는 그 함수 안에서만 사용자 인터프리터에 설치된 cython, cppyy, maturin, PyYAML 같은 패키지를 import합니다. 설치되어 있지 않으면 명확한 오류를 내고, 커널 안에서와 `python file.py`에서 똑같이 동작합니다. 모듈 수준이나 커널 기동 경로에서는 절대 import하지 않습니다. NFR-K2 검사는 이 함수들만 허용 목록으로 둡니다.

### D15. 허브 API는 Cloudflare Workers, 릴레이는 UDP가 되는 호스트, 계정은 GitHub 로그인

사용자 결정(2026-10-03): "dns는 클라우드 플레어고 허브 운영은 허브가 가볍다면 클라우드 플레어 워커를 쓰고 싶어. 계정 생성은 내가 분명히 OpenAI 로그인으로 한다고 했을 텐데?" 이어서 같은 날: "OpenAI 로그인은 엠버 서버에서 사용자가 자체적으로 하는걸로 하고 허브는 깃허브 로그인으로 하자." 그래서 허브(SPEC §10)를 이렇게 바꿉니다.

- **허브 API는 Cloudflare Worker입니다(`hub/worker/`).** 허브가 하는 일 대부분은 서명 검증 한 번과 작은 행 몇 개를 읽고 쓰는 HTTP 요청입니다(기기 10대면 하루 수천 건). 이 정도면 Workers로 충분히 가볍고, DNS가 이미 Cloudflare라 ACME TXT 게시(FR-H5)도 같은 계정의 API 토큰 하나로 됩니다. ash 뷰어는 Workers 정적 자산으로 냅니다.
- **언어는 TypeScript입니다(workers-rs가 아님).** Workers의 1급 언어라 D1·정적 자산·Rate Limiting·Cron 바인딩을 그대로 쓰고, `@cloudflare/vitest-pool-workers`(miniflare)로 실제 D1 위에서 테스트합니다. Web Crypto에 ed25519가 있어 서명 검증에 의존성이 없습니다. workers-rs는 `iroh-dns`의 `SignedPacket`을 재사용할 수 있다는 장점이 있지만, wasm 빌드 도구(worker-build)와 더 큰 번들, 덜 성숙한 D1 바인딩을 떠안습니다. 다시 구현하는 iroh 부분은 pkarr 패킷 형식과 DNS 응답 파싱 약 200줄뿐이고, 형식이 iroh-dns 1.3과 같은지는 테스트와 배포 후 Rust 쪽 시험 벡터로 확인합니다.
- **저장소는 D1 하나입니다.** 허브가 원자적으로 해야 하는 일(일회용 거래와 챌린지 소비, "더 새 패킷만" 저장, 기기 링크를 한 번만 받기)은 모두 SQLite 한 문장(`DELETE … RETURNING`, 조건부 upsert, 조건부 `UPDATE`)으로 됩니다. Durable Objects는 지금 필요 없고, 릴레이를 Container로 옮길 때만 그 바인딩으로 들어옵니다.
- **릴레이는 UDP를 받는 곳에 둡니다(`relay.darkpyonix.dev`, `hub/server/`).** Workers와 Containers는 들어오는 UDP를 받지 않아 iroh의 QUIC 주소 발견(QAD, UDP 7842)을 낼 수 없습니다. QAD가 없으면 기기가 자기 공인 주소를 몰라 직접 연결이 줄어듭니다. 그래서 작은 VPS에서 iroh-relay와 QAD를 함께 돌리는 것으로 시작하고, ember NFR-N1 측정에서 QAD를 끈 직접 연결 비율도 기준(85%)을 넘으면 릴레이를 Cloudflare Container로 옮깁니다(SPEC FR-H3). 릴레이는 누구를 들일지 Worker에 묻습니다.
- **`hub/server`(axum 크레이트)는 릴레이 호스트로 남깁니다.** iroh-relay 서버 크레이트를 쓰는 Rust 코드라 VPS에서 그대로 돌고, Worker로 옮긴 API·SQLite 부분은 빌드할 수 있을 때 걷어 냅니다. 그 전까지 그 부분은 배포하지 않는 D15 이전 구현입니다.
- **계정은 GitHub 로그인입니다(FR-H6).** 인가 코드 + PKCE(S256) + state로 GitHub 사용자 ID를 계정의 정체로 삼고, GitHub 토큰은 사용자 정보를 읽은 뒤 바로 폐기합니다. 기기는 기기 링크로 그 계정에 들어옵니다(FR-H1). 원격 호스팅 서비스가 "Sign in with ChatGPT"를 쓰려면 OpenAI의 신청과 승인이 필요하고(웹사이트 통합은 2026-10 현재 일부 상업 파트너 대상 시범), 허브가 받을 수 있는 OpenAI ID 토큰도 없습니다. ember server가 동적 등록으로 받는 `client_id`는 설치마다 다르고 그 사용자에게 묶여 있어서, 허브가 그 토큰을 받으려면 audience를 검사하지 않아야 합니다. 그러면 사용자가 로그인한 아무 앱의 ID 토큰으로도 그 사용자 계정을 가로챌 수 있습니다. 그래서 OpenAI 로그인과 플랜 사용은 ember server에만 두고(PROJECT Q2), 허브는 GitHub를 씁니다.

### D16. REST 경로에 버전을 넣지 않습니다

사용자 결정(2026-10-03): "REST API의 버저닝은 죄악이야". 매니저 API(`/api/v1/...`)와 허브 API(`/v1/...`, `/internal/v1/...`, `/admin/v1/...`)에서 버전 조각을 뺍니다. 매니저는 `/api/kernels`, 허브는 `/devices`, `/config`, `/internal/relay/admit`, `/admin/disconnect`처럼 씁니다.

- **이유.** 경로의 버전은 "언젠가 계약을 깨도 된다"는 허락입니다. 깨진 계약은 서버가 `/v1`과 `/v2`를 함께 들고 있어야 하고, 클라이언트(ember, ash, VS Code·IntelliJ 확장, 에이전트 CLI)는 어느 판을 부를지 골라야 합니다. 우리 클라이언트는 모두 우리가 만들고, 허브와 매니저 모두 한 곳에서 배포합니다. 판을 둘 이유보다 깨지 않을 이유가 큽니다.
- **대신 더하기만 합니다.** 응답에 필드를 더하고, 선택 요청 필드를 더하고, 새 경로와 새 오류 `code`를 더하는 것은 언제든 됩니다. 클라이언트는 모르는 필드를 무시합니다(커널 프로토콜 PR-4와 같은 규칙). 있는 필드·경로의 이름을 바꾸거나, 지우거나, 뜻이나 타입을 바꾸지 않습니다.
- **바꿔야 할 때는 옆에 새로 만듭니다.** 새 필드나 새 경로를 더하고, 옛것은 OpenAPI에 `deprecated: true`로 표시해 남깁니다. 옛것을 부르는 클라이언트가 없다고 확인된 뒤에만 지우고, 그 삭제는 SPEC 변경으로 남깁니다.
- **기능 발견은 문서와 설정으로 합니다.** 클라이언트는 판 번호로 기능을 짐작하지 않고, 필요한 필드나 경로가 있는지 봅니다. 허브는 `GET /config`, 매니저는 `GET /api/manager`와 `/docs/manager.openapi.yaml`이 그 자리입니다.
- **`/config`의 `api_version`은 지웁니다.** 계약을 깨는 변경에서만 올리던 정수인데, 계약을 깨지 않기로 했으니 영원히 1입니다. 남겨 두면 클라이언트가 그 값을 검사하게 되고, 그것이 다시 판 올리기를 부릅니다. 배포된 빌드를 알리는 `hub_version`(정보용 문자열, 클라이언트가 분기하지 않음)은 남깁니다. 아직 1.0 전이라 이 필드 삭제를 허용하는 마지막 깨는 변경으로 둡니다.
- **범위.** REST 경로만입니다. 서명 대상 문자열의 도메인 구분자(`darkpyonix-hub/v2/link`, `darkpyonix-hub/v1/register`)는 서명을 다른 용도와 섞지 않으려는 것이라 경로 버전이 아니므로 그대로 둡니다. 커널 와이어 프로토콜의 `dkp` 핸드셰이크 버전(PR-4)도 REST가 아니어서 그대로입니다. 정적 자산은 `/ash/` 아래에만 두어, 버전 조각이 빠진 API 경로와 겹치지 않게 합니다.

### D17. 비밀번호와 마스터 토큰은 매니저마다, 접근 토큰은 커널마다 둡니다

사용자 결정(2026-10-03): "원 설계대로 복구". 2025 설계(`설계초안/`의 API 명세서와 Request/Response 페이지)의 인증 계열을 되살립니다. 2026 재설계는 이것을 빼고 매니저 마스터 토큰과 공유 토큰만 남겼는데, 사용자 승인이 없었습니다(§5).

- **비밀번호와 마스터 토큰은 매니저마다 하나입니다.** 사용자 확인(2026-10-04): "매니저 단위 맞아." 2025 API 명세서 요약표의 네 기능이 매니저 단위입니다. 로그인 `GET /auth`, 비밀번호 재설정 `PUT /auth/password`, 마스터 토큰 재설정 `PUT /auth/tokens/master`, 공유 토큰 재설정 `PUT /auth/tokens/shared/{token_type}`입니다. 경로는 D16에 따라 `/api/auth…`입니다(SPEC FR-A4). 이 마스터 토큰이 전용 매니저의 마스터 토큰(SPEC FR-M4)입니다. 2026-10-03 초안의 파일마다 비밀번호는 지웁니다.
- **접근 토큰은 커널마다 둡니다.** 2025 상세 페이지의 `/kernels/{kernel_id}/tokens/initial`, `/tokens/auth`, `/tokens/{token}/verify`, `/tokens/share`는 그 커널에 접근하는 토큰입니다. 사용자(2026-10-04): "아니, 그게 아니고 해당 커널에 접근 가능한 토큰을 말하는거야. 매니저가 여러개잖아." 2025 데이터 구조도 토큰을 `File`에 두었습니다(`class File: kernel_id, tokens, cells`). 그래서 이 토큰은 어느 매니저로 들어와도 통합니다(SPEC FR-A6).
- **접근 토큰은 런타임 홈의 커널 토큰 저장소에 둡니다.** `~/.darkpyonix/tokens/<kernel_id>.json`(0600, 폴더 0700)에 토큰의 SHA-256과 권한, 파일 경로를 둡니다(PROTOCOL §6). 같은 계정의 매니저는 모두 이 파일을 읽어 검사하므로, 어느 매니저로 들어와도 같은 토큰이 통합니다. 매니저 사이에 통신이 필요 없고, 커널이 꺼져 있어도 검사됩니다. 다른 곳을 고르지 않은 이유는 셋입니다. 한 매니저의 `manager.db`는 다른 매니저가 읽지 못하고 임시 매니저에는 없습니다. 커널 메모리는 커널이 멈추면 사라지는데 토큰은 남아야 합니다(FR-A5). 파일 옆(`__runs__/`)은 Git에 올라가는 것이 기본이라(D8) 토큰 해시가 저장소와 다른 기계로 퍼집니다. 커널은 여전히 토큰을 검사하지 않습니다(D5). 커널은 자기 파일이 지워진 것을 보면 저장소를 지우는 일만 합니다. 이 위치는 리더 결정, 사용자 확인 대기입니다(PROJECT Q16).
- **흐름은 2025 그대로입니다.** 커널을 열 때 초기 토큰을 받고(`password_required: true`), 매니저에 비밀번호가 아직 없으면 그 토큰으로 정합니다. 그 뒤로는 비밀번호로 로그인해 마스터 토큰(`GET /api/auth`)이나 커널 접근 토큰(`POST /api/kernels/{kernel_id}/tokens/auth`)을 받습니다. 비밀번호로 마스터 토큰을 다시 만들고, 마스터 토큰으로 타입별 공유 토큰을 다시 만듭니다.
- **토큰 수명도 2025 그대로입니다.** "커널이 지워지면 토큰은 보관되나, 파일이 지워지면 토큰도 지워져야 함", 그리고 "공유 버튼을 눌렀다가 다시 해제하고 다시 누르는 경우 토큰 초기화 필요"(SPEC FR-A5). 커널은 파일에 묶인 논리 커널이고 프로세스는 오가므로(D1, D2), 토큰은 프로세스가 아니라 파일을 따라갑니다.
- **매니저가 검사합니다.** 비밀번호와 마스터·매니저 공유 토큰은 그 매니저의 `manager.db`에 해시로만 둡니다. 커널은 인증하지 않습니다(D5).
- **경로 표기.** 2025 문서는 요약표(매니저 단위)와 상세 페이지(커널 단위) 두 가지를 적었고, 2026-10-03 초안은 이것을 같은 기능의 두 표기로 읽어 파일마다 비밀번호를 두었습니다. 사용자 확인으로 둘은 다른 범위입니다. 요약표는 `/api/auth…`, 상세는 `/api/kernels/{kernel_id}/tokens/…`에 둡니다(PROJECT Q10). 상세의 `/kernels/{kernel_id}/password`는 요약표의 `/auth/password`와 같은 기능이라 두지 않습니다.

### D18. 권한은 2025 모델 `viewer1`·`viewer2`·`viewer3`·`admin`과 `user_permission: "write"`입니다

사용자 결정(2026-10-03): "원 설계대로 복구". 2025 설계의 권한입니다(`설계초안/` Request/Response "tokens/auth" 페이지).

| 권한 | 2025 정의 |
|---|---|
| `viewer1` | 코드만 적혀 있고 History 없음, 코드 실행 불가 |
| `viewer2` | 코드 O, History O, 코드 실행 불가 |
| `viewer3` | 코드 O, History O, 코드 실행 가능 |
| `admin` | 전부(공유 관리 포함) |

- **`user_permission: "write"`.** 2025 요청 시그니처는 잠금, 잠금 해제, 실행에 `user_permission: str = "write"`를, 공유 설정에 `user_permission: str = "admin"`을 둡니다. 2025 잠금 오류는 `403 INSUFFICIENT_PERMISSION`, "Read-only access, cannot edit cells"입니다. 그래서 요청은 `user_permission: "write"`를 실을 수 있고, 매니저는 토큰이 쓰기를 허락하는지 봅니다. 결정은 토큰이 합니다. 쓰기를 허락하지 않는 토큰은 이 인자가 있어도 거절됩니다.
- **쓰기는 `viewer3`와 `admin`입니다.** 2025에서 실행에 `write`가 필요하고 `viewer3`가 실행할 수 있으므로, `write`를 가진 쪽은 `viewer3`와 `admin`입니다. 그래서 셀 편집과 잠금도 `viewer3`부터입니다. 이 대응은 2025 문서에서 끌어낸 것이라 사용자 확인 대기입니다(PROJECT Q13).
- **`editor` 등급은 지웁니다.** 리더가 사용자 승인 없이 더한 등급입니다(§5). D16은 계약을 더하기만 하라고 하지만, 승인 없이 들어간 값을 되돌리는 일이고 아직 1.0 전이라 지웁니다.
- **커널은 권한을 다시 검사하지 않습니다(D5).** 커널의 `doc.*` 요청 권한 검사와 `forbidden` 오류는 지웁니다.

### D19. 협업 동기화는 2025 WebSocket 명세를 따릅니다

사용자 결정(2026-10-03): "원 설계대로 복구". 2025 설계의 `/ws/kernels/{kernel_id}?token={token}`을 `/api/ws/kernels/{kernel_id}`(D16)로 되살립니다. 메시지 이름과 필드는 2025 그대로입니다(PROTOCOL §5).

- **받는 메시지:** `request_code`, `request_history`, `request_locks`, `start_typing`, `cell_focus`. 2025 명세에는 다른 사용자의 블러 알림(`other_user_blur`)이 있지만 그것을 일으키는 송신 메시지가 없어서 `cell_blur`를 더합니다.
- **보내는 메시지:** `code_data`, `history_data`, `locks_data`, `users_focus_data`, `other_user_focus`, `other_user_blur`, `cell_locked`, `cell_unlocked_with_code`, `execution_started`, `execution_output`, `execution_complete`, `execution_error`, `execution_interrupted`.
- **WebSocket은 커널이 받습니다.** 매니저가 토큰과 권한을 확인한 뒤 연결을 넘깁니다(D6). 커널은 표준 라이브러리(`hashlib`, `base64`, `struct`)로 RFC 6455를 구현합니다. 그래서 매니저가 죽어도 동기화가 이어집니다.
- **편집, 잠금 해제, 실행, 인터럽트는 2025처럼 REST입니다.** 2025 명세도 "클라이언트 → HTTP POST /kernels/{kernel_id}/execute → 서버가 실행 과정을 WebSocket으로 모든 클라이언트에 브로드캐스트"였습니다. 이 요청들은 매니저가 받아 DKP/1로 커널에 보내고, 커널이 WebSocket으로 퍼뜨립니다.
- **SSE 이벤트 스트림은 남깁니다.** `EventSource`만 쓸 수 있는 클라이언트와 CLI를 위해서이고, 계약을 지우지 않는다는 D16과도 맞습니다. 2025 이름이 없는 문서 이벤트(셀 생성·수정·삭제·이동, 바깥 편집 다시 읽기)는 WebSocket에서도 `{"type": "event", "event": …}`로 PROTOCOL §3.4·§4 이벤트를 그대로 싣습니다.

### D20. Android와 iOS에서는 앱 안에 미리 정한 프로세스에서만 노트북을 실행합니다

사용자 결정(2026-10-03): "안드로이드랑 iOS의 경우 PyREPL 구현처럼 별도 미리 정의된 프로세스 내에서만 노트북이 실행 가능하도록 하면 되는거야."

- **PyREPL 방식.** thisisthepy/PyREPL(Android, Kotlin Multiplatform + Chaquopy)은 `AndroidManifest.xml`에 커널 서비스 `InAppKernelService0`…`9`를 미리 선언하고, 각각을 정해진 프로세스(`:kernel0`…`:kernel9`, `MAX_WORKERS = 10`)에서 포그라운드 서비스로 돌립니다. 앱은 `workdir`과 `filename`을 담은 Intent로 서비스를 시작하고, `signum`으로 인터럽트합니다. 앱 프로세스 안의 `UIThreadKernelService`와 `:lab` 프로세스의 `InAppLabServerService`도 같은 방식입니다.
- **그래서 모바일에는 데스크톱의 세 가지가 없거나 다릅니다.** 커널을 아무 인터프리터로 띄워 멀티캐스트로 찾는 발견(D4)이 없습니다. 앱이 자기 프로세스 목록을 이미 압니다. 커널과 매니저 사이 소켓 넘김(D6)도 없습니다. 앱 안의 클라이언트가 같은 앱의 커널 프로세스에 직접 붙습니다. 분리된 매니저 프로세스(D10)도 필요 없거나 앱 안에 들어갑니다. 파일당 커널 하나(§2 조건 4), 멈춤은 인터럽트(§2 조건 5), 실행 기록(D8)은 그대로입니다.
- **어디서 다루나.** 모바일 실행 경로는 이 저장소가 아니라 Ember 모바일 앱(dioxus-compose / compose-rust 위의 앱)이 다룹니다. 이 저장소가 주는 것은 커널과 런타임 API의 파이썬 코드와 DKP/1·nbformat 형식입니다. 모바일 설계와 이슈는 Ember 쪽에서 엽니다(SPEC FR-D3). 상태: 계획.

### D21. 이 저장소는 Apache License 2.0입니다

사용자 결정(2026-10-03): "core·ember는 Apache, ash는 MPL 유지". 그래서 이 저장소(core)의 라이선스를 MIT에서 Apache-2.0으로 바꿉니다. 저작권자는 그대로 DarkPyonix입니다. `darkpyonix-ember`도 Apache-2.0이고, `darkpyonix-ash`는 MPL-2.0을 유지합니다.
